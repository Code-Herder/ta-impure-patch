Design plan·tagpu render thread·reviewed draft, 2026-09-11

Frame Packet Exchange

One construct for everything that crosses between the game thread and the render thread. The game thread publishes a packet of exactly what the renderer needs, once per drawn frame, through a wait-free four-slot mailbox. The renderer stops reading and writing the engine's per-frame state. What it still reads, the per-level assets, stays behind the fence that already exists until an asset channel retires it.

1 · the problem the audit left

Every cross-thread read is its own proof, and the proofs keep failing silently

The engine is single-threaded in play: one game thread owns every byte under main = *(char**)0x511DE8. The fork adds a GL render thread that re-renders the world from that memory once per presented frame. Each read site carries its own argument (a bound, a lifetime, an ordering). The 2026-09-11 audit found the arguments mostly hold, but the shape guarantees the next one will not:

  • The fence covers the teardown, not the load. tagpu_reclaim holds the renderer off while 0x491B60 frees a level. The next level's load (0x4854A0) stores the unit array's begin, memsets, allocates twice and only then stores end, with the renderer live. That pair is the one open hazard, in every launch, independent of alignment.
  • Poses are read mid-tick. The unit pass reads each piece's P_POS/P_TURN from the engine with no interlock, so a unit can be drawn with its pieces mixed across a tick boundary. The unit's three-dword anchor likewise.
  • The renderer also writes. The eye, its scroll target, the minimap view rect, the viewport edges and ScrollSpeed are stored into engine words from the render thread. main is misaligned afresh at every launch (0x41D920 pads by 7·(GetTickCount()%1000)), so those stores can tear. They are tolerated only because a torn coordinate is clamped. Pointer slots had to be moved to a game-thread handshake already (the camera follow, G13u).
  • Seven channels exist, seven proofs. Two aligned dwords for the font at GUI hook 8; three fog buffers swapped under a critical section with a retire ring; request and ack levels for the zoom; a game-thread arena of order markers; the reclaim pass counters with a 4096-entry ring that leaks on overflow and a one-second teardown timeout; the GL UI's op queue and arena, with a second publisher on the loader thread for the minimap picture and an engine address inside its string op (section 9); the scenario applier's state word. Each is right on its own terms. Each was a separate review.
  • Three bugs of this class shipped silently before the fence: the 200v200 faults at 95 s, the fog guard whose root cause was never found, and a producer gated on a value the other thread published (G13s). They do not throw. They corrupt a frame days later, one launch in many.
2 · the proposal

Publish on the thread that owns the memory, hand over through a cell neither thread waits on

Channels, one primitive.

game → render Frame packet, once per taken frame
After the engine has drawn and flipped an in-play frame, the game thread copies exactly what the renderer needs into a slot of our memory, in our aligned layout, bounding every value as it copies, and swaps the slot's index into the shared cell. It does this only when the renderer has taken the previous packet, so the copy runs at the present rate, not the engine's draw rate. The renderer takes the newest complete packet at the top of its frame and draws from it alone.
render → game Commands, applied before the engine draws
Everything the renderer wants changed (the eye, its scroll target, the minimap rect, the viewport widen, ScrollSpeed, the follow release, tooling requests) becomes a record the game thread applies at the start of the next in-play draw. The anchor step travels as a delta consumed once; the eye hold as a level. The renderer predicts with its own unacknowledged deltas so zoom-to-cursor keeps its current feel.
game → render Out-of-game packet, at teardown
No in-play frame is drawn between levels, so nothing would be published. The teardown's post hook publishes a header-only packet with in_game = 0; every world consumer gates on it. Without this the renderer would keep drawing the dead level over the menus.
game → render Level packet and assets, optional end state
The per-level arrays (tile set, tile map, height map, feature defs, type table, minimap picture) and the pointer-linked assets the renderer still walks (model templates, GAF frames, fonts) can be copied once per level or on first sight through more instances of the same exchange. Until that lands, those reads stay allow-listed behind the reclaim fence, which is measured and proven for exactly that lifetime.

Why this is "by construction" in the project's sense

The publisher runs on the thread that owns the memory, inside the engine's own frame, at a point where the engine has just drawn from the same state. "Is the engine mid-update?" is answered by "no, we are the engine's thread". Lifetime, ordering and tearing vanish for the copy. What remains is the data bound (model_id < UNITINFOCount, counts against capacities), applied once, in one file, against counts that are consistent because nothing else is running on this thread. The exchange brings four ordering obligations and one init obligation of its own, proven once in section 4.

3 · one frame, end to end

Commands before the draw, publish after the flip, acquire at the top of the render frame

Both directions hang on one observer of DrawGameScreen 0x468CF0, which tagpu_menu.c already observes with the same stolen bytes, so the chaining is proven. The observer acts only when the return address is 0x4969D2, the in-play frame callback's call. That gate excludes the shell, the screenshot function's sweep of the eye (it calls DrawGameScreen in a loop without flipping) and the movie recorder for free, and it is what guarantees the loader thread has finished before the first publish (section 8). The engine draws 330 to 4900 times a second depending on resolution and scene, while the presenter shows about 60, so the publisher copies only when the cell has no fresh packet waiting.

A worked example

First the types, then a packet built from them. Every field names the engine location the publisher reads it from and the bound it applies, so the listing doubles as the census of what still has to be read from engine memory, and where: in one file, on the game thread.

// tagpu_packet.h — the frame packet's tables. Every field says where the
// publisher reads it (game thread, in-play frames only) and the bound it applies.
// Nothing is packed; the padding is written out. "KEY" = an engine address that
// crosses as an opaque identity and is never dereferenced by the renderer.

typedef struct PK_UNIT {                 // 72 B, one per LIVE unit, in engine slot order
    uint16_t slot;                       // index in the engine's unit array (stride 0x118)
    uint16_t id;                         // unit+0xA8, the stable in-game id: the lerp's key
    uint32_t state;                      // unit+0x110 state bits (bit28 alive, bit14 excluded)
    int32_t  pos[3];                     // unit+0x6A / +0x6E / +0x72, 16.16: x, altitude, depth
    uint16_t rot[3];                     // unit+0x64: bank, heading (the yaw at +0x66), pitch; 65536 = 360 deg
    uint16_t model_id;                   // unit+0xA6; the entry is DROPPED unless < UNITINFOCount (main+0x1438F)
    uint16_t type_row;                   // the UnitDef row of unit+0x92, stride 0x249
    int16_t  health;                     // unit+0x108, s16
    uint8_t  owner;                      // unit+0xFF, player id
    uint8_t  cloak;                      // unit+0x10E, bit2 = actively cloaked
    uint8_t  flags;                      // bit0 = the composite has a depth plane (Object3do+0x10 -> +0x14)
    uint8_t  pad0;
    float    nano;                       // unit+0x104, fraction of the build REMAINING
    int16_t  cargo_first, cargo_next;    // unit+0x8A / +0x8E, resolved to PACKET indices, -1 = none
    uint32_t squad;                      // unit+0xAC, read as a dword because 0x469C55 does
    uint32_t o3_key;                     // unit+0x9E, the Object3do address, KEY (the bake caches key on it)
    uint16_t nparts;                     // Object3do+0x00
    uint16_t piece_n;                    // nparts if the unit is inside the widest zoom rect + margin, else 0
    uint16_t bturn[3];                   // Object3do+0x18 / +0x1A / +0x1C, the cached body turn the compose baked
    uint16_t pad1;
    uint32_t piece_off;                  // byte offset of this unit's PK_PIECE run in the arena
    uint8_t  ground_h;                   // feature cell +0x04 under the anchor
    uint8_t  pad2[3];
} PK_UNIT;

typedef struct PK_PIECE {                // 20 B, piece_n per unit, in the model's own order (parents first)
    int32_t  pos[3];                     // prim+0x04 P_POS, the COB MOVE delta, 16.16
    uint16_t turn[3];                    // prim+0x10 P_TURN, the COB TURN triple, 65536 = 360 deg
    uint8_t  flags;                      // prim+0x28 P_FLAGS
    uint8_t  pad;
} PK_PIECE;                              // prim = Object3do+0x22 + i * 0x36, walked on the game thread only

typedef struct PK_WRECK {                // 28 B, one per live wreck record
    uint16_t rec;                        // record index at main+0x1420B, stride 0x30
    uint16_t def;                        // FeatureDef row (main+0x1426F, stride 0x100)
    int32_t  pos[3];                     // record+0x08 / +0x0C / +0x10, 16.16
    uint32_t o3_key;                     // record+0x04, KEY
    uint16_t nparts, piece_n;            // as PK_UNIT
    uint32_t piece_off;
} PK_WRECK;

typedef struct PK_ANCHOR {               // 12 B, one per feature-grid cell in the gather rect that anchors a feature
    uint16_t col, row;                   // cell in 16-px tiles; the grid is main+0x14287, 13 B per cell
    uint16_t def;                        // cell+0x08 FT_DEFIDX, live when < 0xFFFB
    uint16_t wreck;                      // cell+0x0A FT_WIDX, valid when flags bit0
    uint8_t  flags;                      // cell+0x0C FT_FLAGS: bit0 wreckage present, higher bits seen-by-player
    uint8_t  height;                     // cell+0x04
    uint8_t  pad[2];
} PK_ANCHOR;                             // per FRAME, not per level: def, flags and wreck change every tick

typedef struct PK_PROJ {                 // 56 B, from the 300-slot array main+0x141F7 (count main+0x141F3), stride 0x6B
    int32_t  pos[3];                     // rec+0x04 / +0x08 / +0x0C, 16.16: x, altitude, depth
    int32_t  start[3];                   // rec+0x10 / +0x14 / +0x18, the tail
    int16_t  turn[3];                    // rec+0x34
    int16_t  spin;                       // rec+0x64
    int32_t  spawn, death;               // rec+0x42 / +0x46, ticks
    uint16_t ground_h;                   // rec+0x5E
    int16_t  hidden;                     // rec+0x60, drawn only when 0
    uint32_t weapon_key;                 // rec+0x00 WeaponDef, KEY; its fields below are resolved here
    uint8_t  render_type, color, color2; // weapon+0x10C / +0x10D / +0x10E
    uint8_t  owner;                      // rec+0x52 attacker -> unit+0xFF, or 0xFF

} PK_PROJ;

typedef struct PK_EXPL {                 // 36 B, from main+0x1491F (count main+0x1491B), stride 0x54
    int32_t  pos[3];                     // rec+0x1C / +0x20 / +0x24
    int16_t  turn[3], pad;               // rec+0x4C
    uint32_t model_key;                  // rec+0x00, KEY
    uint32_t anim1_key, anim2_key;       // rec+0x04 / +0x10 anim states: the sequence at +8 as a KEY
    uint16_t frame1, frame2;             // the u16 frame at +0 of each
} PK_EXPL;

typedef struct PK_DEBRIS {               // 24 B, from the 100 static slots 0x511DF0..0x511F80 (in .data, not under main)
    int32_t  pos[3];                     // slot+0x16 / +0x1A / +0x1E
    int16_t  turn[3], pad;               // slot+0x12
    uint32_t model_key;                  // slot+0x00, KEY
} PK_DEBRIS;

typedef struct PK_POBJ {                 // 16 B, one per particle object across the ten layers at *(main+0x38D77)
    uint8_t  cls;                        // by vtbl: 0 grey smoke, 1 dark smoke, 2 fire, 3 flare, 4 wake, 5 nanolathe
    uint8_t  layer;                      // obj+0x0C, 0..9 = the draw depth
    uint16_t n_sub;                      // (obj+0x14 - obj+0x10) / the class stride, capped by the arena
    uint32_t sub_off;                    // first PK_PSUB in the arena
    int32_t  tick, end_tick;             // obj+0x08 / +0x04
} PK_POBJ;

typedef struct PK_PSUB {                 // 16 B, one per sub-particle; the class strides 0x20..0x44 collapse to this
    int32_t  pos[3];                     // 16.16, at +0/+4/+8 (nanolathe) or +4/+8/+0xC (the rest)
    union { int32_t frame; uint8_t colour; } u;   // frame at +0x14 (smoke) or +0x2C (fire, flare); colour at +0x30 / +0x28
} PK_PSUB;

    uint32_t in_game;                    // 0 from the teardown post hook: draw no world

    uint32_t cmd_ack_seq;                // the last command applied before this draw (section 7)
    int32_t  eye[2], scroll_to[2];       // main+0x1431F / +0x14323, +0x14327 / +0x1432B
    int32_t  vp[4];                      // the TRUE 1x rect L, T, W, H via tagpu_vpwide_true_rect(), never raw main+0x37E27
    int32_t  map_w16, map_h16;           // main+0x14233 / +0x14237
    int32_t  map_pxw, map_pxh;           // main+0x14223 / +0x14227
    int32_t  view_cells[2];              // main+0x1423B / +0x1423F
    uint32_t udef_count;                 // main+0x1438F UNITINFOCount, the bound on model_id
    uint32_t unit_slots;                 // u16 main+0x14351 = 10 x MaxUnits + 1, the units table's capacity
    uint16_t los_type;                   // main+0x14281: bit1 true LOS, bit3 grid current
    uint16_t gfx_opt, ui_gates;          // main+0x37F06 (bit2 Shadow, bit3 TShadow), +0x37F2F (bit2 SelBoxes)

What the consumer does with it. The driver calls acquire once and passes the pointer down. The native pass walks units[] and indexes pieces[] by each unit's piece_off; it no longer knows what an Object3do is. The lerp module keeps the previous packet as well and blends the pieces of the same stable id between tick 2060 and tick 2061 by wall clock, from the producer's tick_start stamp rather than its own guess, and never past u = 1. The fx pass reads PK_PROJ with the weapon's render type and colours already resolved, so the pointer chase from projectile to weapon to attacker that it does today on the render thread is gone.

What the producer did to make it. One walk of the engine's unit array from begin to end, both read on the thread that stores them, so the pair is never skewed. For each live unit: copy the fields, drop the entry if model_id ≥ UNITINFOCount, copy its pieces if the unit is inside the widest zoom rect plus a margin, resolve cargo links to packet indices. Then the wrecks, the feature anchors in the gather rect, the projectile, explosion and debris arrays, the ten particle layers, the fog grid, the three minimap surfaces the game thread repaints each draw, the cursor's pixels. Then the tail sequence, then one xchg.

Cost envelope. The publish is a gather, not a memcpy: about 30 scattered loads per unit plus its pieces. Estimated 0.1 to 0.15 ms for this scene and about 1 ms at a few thousand drawable units, before particles and anchors. Gated to the present rate it is about 1 % of the game thread; ungated at the engine's draw rate it would be 6 to 7 %. It is a gate, not an assumption: the publisher is timed with the performance counter and the budget is stated before the first landing (section 11).

4 · the primitive

Four slots, one aligned word, two exchanges

The standard wait-free single-producer, single-consumer "latest value" exchange. Slots have roles, not owners fixed for life: W is the one the game thread is filling, READ and PREV are the two the renderer holds (current and previous, for interpolation), and the fourth sits in the cell, either fresh (published, not yet taken) or stale (returned by the renderer, waiting to be reused). The cell is one 32-bit aligned word in our static storage: two index bits plus a FRESH bit, reserved bits asserted zero.

Both sides, in C

The whole of the cross-thread state is one word. Each side exchanges a slot it owns into the cell and takes whatever was there, which is what keeps the permutation a permutation without a lock. The exchange is spelled with the GCC atomic builtin: on this toolchain InterlockedExchange expands to __sync_lock_test_and_set, whose documented contract is acquire-only, and two of the four orderings the protocol needs are release. Same instruction (xchg, implicitly locked), stronger contract.

/* tagpu_packet.c — the exchange, as corrected by the protocol review. */
#define PKX_IDX    0x3u          /* two index bits                              */
#define PKX_FRESH  0x4u          /* set by publish, cleared by acquire          */

static PACKET* volatile s_slot[4]; /* entry i written only by slot i's owner    */
static LONG             s_cell;    /* idx | PKX_FRESH — the ONLY shared word    */
static unsigned s_write, s_seq;    /* game thread only                          */
static unsigned s_read, s_prev;    /* render thread only                        */
static uint32_t s_frame_head;      /* render thread: head latched at acquire    */

#define XCHG(v)  __atomic_exchange_n(&s_cell, (LONG)(v), __ATOMIC_ACQ_REL)
#define PEEK()   __atomic_load_n(&s_cell, __ATOMIC_RELAXED)

/* DLL ATTACH, before either thread exists — never lazily. */
void tagpu_packet_init(void)
{
    /* allocate four slots at the initial high-water mark; head_seq 0 = no packet */
    s_write = 0; s_read = 2; s_prev = 3;                  /* {0,1,2,3}: a permutation */
    __atomic_store_n(&s_cell, 1L, __ATOMIC_RELEASE);      /* slot 1 in the cell, stale */
}

/* GAME THREAD, from the DrawGameScreen observer's `after`, in-play frames only. */
void tagpu_packet_publish(void)
{
    PACKET* p;
    if (PEEK() & PKX_FRESH) return;                       /* the renderer has not taken the last one */
    p = commit_if_needed(s_write);                        /* our own slot: more pages at the same address, never a new block */
    p->head_seq = ++s_seq;                                /* head BEFORE the payload            */
    __atomic_signal_fence(__ATOMIC_SEQ_CST);
    fill(p);                                              /* every engine read lives here; truncates, never fails */
    __atomic_signal_fence(__ATOMIC_SEQ_CST);
    p->tail_seq = s_seq;                                  /* tail AFTER the payload             */
    {   /* P1: payload visible before the index. P2: the next fill of the slot we
           receive stays after this exchange. Both from the ACQ_REL xchg.       */
        LONG old = XCHG(s_write | PKX_FRESH);
        s_write = (unsigned)(old & PKX_IDX);              /* stale, or never taken: ours now    */
    }
}

/* RENDER THREAD, exactly once per frame, at the top of the overlay driver. */
const PACKET* tagpu_packet_acquire(const PACKET** prev)
{
    if (PEEK() & PKX_FRESH) {
        /* Tick-aware give-back: a packet of the SAME tick replaces read and keeps
           prev, so the interpolation pair always spans two distinct ticks.       */
        unsigned give = (peek_tick_of_cell() == s_slot[s_read]->tick) ? s_read : s_prev;
        /* C2: our last loads of `give` precede this exchange. C1: our loads of
           the new slot follow it and depend on its result.                       */
        LONG old = XCHG(give);
        unsigned got = (unsigned)(old & PKX_IDX);
        if (give == s_prev) s_prev = s_read;
        s_read = got;
    }
    s_frame_head = s_slot[s_read]->head_seq;              /* latched for frame_end              */
    *prev = s_slot[s_prev];                               /* NULL if it is from another level   */
    return s_slot[s_read];                                /* unchanged if nothing was fresh     */
}

/* RENDER THREAD, after the frame's LAST read of either packet. */
void tagpu_packet_frame_end(void)
{
    __atomic_signal_fence(__ATOMIC_SEQ_CST);
    if (s_slot[s_read]->tail_seq != s_frame_head) violation("our slot was rewritten during our frame");
}

The tick-aware give-back needs the tick of the packet in the cell before taking it. The consumer may not read a slot it does not hold, so the producer carries the tick in the cell word's spare bits or, simpler, the consumer always takes the fresh packet and then decides which of its now three held packets to hand back at the next acquire. The reference implementation in the protocol review uses the plain form; the choice is the first landing's, and either keeps the permutation.

Why it is safe, in five lines

  • No shared slot. Each side only ever puts into the cell a slot it holds, and takes out the one that was there. Four indices, four roles, always a permutation, provided the init made it one. The producer's own slot is the only one that grows, and it grows in place: each slot's address range is reserved once and pages are committed as the high-water mark rises, so no block ever moves and nothing is ever freed. A rule-breaking cached pointer can only reach a slot's current bytes, never freed memory.
  • No tearing. The cell is one aligned word. The packet's contents are never accessed by both threads at once, so their alignment is a performance property, not a safety one.
  • Four orderings, one instruction. Payload before index (P1) and loads after the exchange (C1) hold on x86 for plain stores already; the give-back directions (P2: the next fill after the exchange, C2: the last loads of the returned slot before it) are what xchg's implicit lock adds. The atomic builtin makes the compiler honour all four; volatile alone would not order the non-volatile payload.
  • No waiting, anywhere. Neither exchange can fail or block. A slow or dead partner changes what the other side sees, never whether it proceeds. The game thread still joins the render thread on a display-mode change and release, and the render thread still holds the fork's critical section during the surface upload; those waits are cnc-ddraw's and pre-date this design.
  • Violations are loud. Head stored before the fill, tail after; the consumer latches the head at acquire and compares the tail at frame end, which catches any overlap of a fill with a frame. Thread identity on both sides, the permutation after every exchange, a canary past the capacity, structural bounds on every table, one acquire per frame, a poison lever that memsets the received slot. The heartbeat prints pub overrun acq taken gap grow commitfail trunc viol, and viol=0 is the first landing's gate.

Foolproof by API shape, not by discipline

Modules never see the exchange. The driver acquires once per frame and hands every pass the same const PACKET* through the frame struct it already passes. A module cannot acquire twice, cannot hold a slot across frames (the pointer it was given is valid for this frame only), and cannot reach the producer's slot at all. The lerp module, the one consumer that needs last frame's data, gets prev from the same call. Anything that needs engine memory is, by construction, game-thread code in the publisher. The same struct is instantiated for the frame packet, the commands, the wide fog grid, and later the level packet, so the proof is written once.

5 · edge cases

When one side stops, bursts, runs ahead, or the level ends

Each case below is the same primitive under a different schedule. None of them allocates per frame, blocks, or reads a slot the other side holds. Three were found by the adversarial review and changed the design; they are marked.

Consumer stuck renderbounded

A GL driver stall, a blocking SwapBuffers. The game thread keeps going: with the FRESH gate it skips the copy entirely (one relaxed load per draw); with a max-age override it alternates between its slot and the one in the cell, forever, in constant memory. When the renderer wakes it takes the latest packet. A stalled game thread would freeze this player's units for everyone, so the sim must never wait on the renderer, and here it does not.

Between levels gamechanged the design

After the teardown the shell flips thousands of times a second but none is an in-play frame, and the render thread keeps running. Today the unit pass stops because the teardown nulls begin; the packet removes that read and replaces it with nothing, so the renderer would draw the dead level's units, wrecks and fog over the main menu and the loading screen. Fix: the teardown post hook publishes a header-only packet with in_game = 0 and the new level generation; every world consumer gates on it.

Producer bursts gamelatest wins

The engine draws 7 to 15 times per presented frame; DeltaTime is 0 to 5 ticks per draw, so consecutive publishes can differ by several ticks. With the FRESH gate one packet per taken frame is copied; any that are skipped show as sequence gaps, counted, not violations. The one packet that must not be lost is the first of each tick, which is why the producer stamps tick_start itself with the performance counter when it first sees GameTime change and carries it in every packet of that tick. Which packet the consumer takes is then irrelevant to the blend.

Same-tick packets and the interpolation pair renderchanged the design

With several publishes per tick, a consumer that hands back prev on every take soon holds two packets of the same tick, and the blend refuses: stepped motion, always. Fix: the acquire is tick-aware; a packet of the same tick replaces read and keeps prev, so the pair always spans two distinct ticks. Units are matched between the two by stable id and level generation, never by table position. Never extrapolate past u = 1: a limb that stopped or reversed would overshoot, and a stalled producer would run off the map.

Consumer faster than producer renderinterpolates

A 144 Hz display over a sim ticking 30 or 60 times a second: most render frames find no FRESH bit and redraw the same packet, one relaxed load each, no cache-line bouncing. With prev and read both held, the lerp blends by wall clock from the producer's tick stamp, as it does today from its own guess.

Units table overflow gamechanged the design

The draft capped the units table at 2048 with a truncation counter. The engine allocates unit slots in per-player blocks, so cutting the walk in slot order would drop the highest-numbered players entirely: in a four-player game past 2048 units, two armies never render for the whole battle. Fix: size the units table to the engine's own slot count, u16 main+0x14351, at most 15001 entries, so unit truncation cannot happen. Cull only the piece arena, by the widest zoom rect plus a margin (never the current zoom level, which the game thread sees a frame late), so off-screen units carry no pieces and cost 72 bytes each.

Slot growth mid-game gamein place, nothing freed

Each slot's address range is reserved once at DLL attach with VirtualAlloc(MEM_RESERVE), at a ceiling well above the worst case (8 MB per frame slot against about 2.3 MB), and pages are committed as the high-water mark rises. A table that would overflow the committed size truncates this frame (a bit per table in the header), and the publisher commits more pages to its own write slot before the next fill. The block never moves, so nothing is ever freed or stranded and no pointer into a slot can dangle. A commit that fails keeps the current size and retries on a later publish rather than pinning it for the session. The pages come from the kernel, not the CRT heap, so fragmentation cannot arise. Anything ever retired is decommitted, not freed: the range stays reserved and inaccessible, so a stale pointer faults at an address that names the packet instead of reading reused memory. Reference counting was considered and rejected: a count cannot see the raw pointer a module copies, and a mismatched release is the use-after-free again. The renderer never holds the write slot and only dereferences indices of slots it holds.

Render thread restarted renderjoined, not killed

On a display-mode change cnc-ddraw sets the run flag false and joins the render thread with an infinite wait; the loop exits only after SwapBuffers. So the old thread is never mid-acquire when it ends, the consumer's READ/PREV indices are module statics the new thread inherits under a full synchronisation, and the GL re-init reads our held slots instead of engine memory. Ownership is by role, never by thread id; the consumer records the new id and continues.

Level change under a held packet gameheader gated

The renderer may hold prev from the old level when the first packet of the new one arrives. Model ids, template keys and piece counts in the old packet refer to a dead level. The acquire hands out prev only when its level generation matches; every per-model cache is keyed on (level_gen, model_id); the lerp's unit key is (level_gen, stable id). The packet carries reclaim's counter as long as reclaim exists, so there is one generation, not two.

A wrong pointer in the publisher gamemoves the fault

Today a bad engine read faults the render thread; after, the game thread. Not worse: an access violation on any thread ends the process, and a fault on the game thread is more likely to leave the engine's own error log naming our address than one on the render thread, which today reads as a freeze. Structured exception handling around the publisher is not a legitimate guard (it makes a wrong offset rarer) and 32-bit mingw has none anyway. The legitimate guards are the bounds against the engine's own counts and the byte-verified hook sites.

Layer coherence rendermeasured, not paired

The render thread composites the engine's software frame, uploaded whenever it wakes, with our overlay from the packet. Publishing after the flip means the packet is never older than the surface, but the skew is up to one engine draw (under 3 ms of game time) either way, and the engine's own copy already races the upload since the fork does not lock surfaces. The UI twin is not paired with the packet either: it travels on the GL UI queue (section 9), which the render thread drains to empty after taking its one packet, so the twin can be ahead of the packet by whatever the queue held. Invisible because nothing in the twin is world-anchored except the engine's own minimap box and dots at 1×, which move under a pixel per engine draw, and the box becomes a header field and a command in landing 2. Plan: stamp a surface sequence in dds_Unlock on in-play flips, echo it and the GUI publisher's flip counter in the packet, count both skews on the heartbeat. If a mismatch is ever seen, the by-construction answer is the surface itself in the packet (2 MB at 1080p, 8 MB at 4K).

Smooth motion keeps working, with a cleaner input

The walking animation is interpolated today by sampling every piece's P_POS/P_TURN on the render thread into two banks of history and drawing the pose at tick T−1 plus the wall-clock fraction of tick T. Under the packet the two held packets are that history: prev and read always span two distinct ticks, the producer stamps when each tick began, and the blend runs over the same PK_PIECE values matched by the stable unit id. Same one-tick latency, same blend, same refusal to extrapolate; the 3.4 MB arena, the pointer-keyed hash and the same-type-reuse residual go away. Unit translation is not interpolated today at all: the sim moves a unit once per tick, 30 times a second at GameSpeed 10 (the rate the engine's own clock display assumes) and 60 at the GameSpeed 20 the project's fixtures land on, and the native pass reads the 16.16 anchor at whatever the tick rate is, which PK_UNIT.pos carries unchanged. At 30 ticks over 60 presents half the frames repeat the previous position today. What improves is that every sample is taken between ticks, so a unit can no longer be drawn with its pieces mixed across a tick boundary, and interpolating positions between the two held packets, which would make translation smooth at 60 fps over a 30 Hz tick, becomes a small option rather than a new sampling problem.

Envelope. About 0.25 MB typical, about 2.3 MB at the worst case the engine allows. Four slots reserve 32 MB of address space and commit only the high-water mark, under 10 MB at the worst case; the process has 726 MiB free below 2 GiB on the reference setup, most of it in two large holes. In exchange the lerp's 3.4 MB pose arena and fogwide's retire ring go away.

Bounds at the copy. model_id against UNITINFOCount, the walk against the engine's slot count, piece count against the model's nparts, every table against its capacity, the fog grid against its dimension cap. A value that fails its bound drops the entry and bumps a counter; the packet is always complete and always valid.

Keys, not pointers. The Object3do, the template, the GAF frame: each may ride as a key the renderer resolves against its own caches. Nothing on the render thread dereferences one. The draft had the cursor frame pointer in the header; the cursor's pixels are copied instead. The font is not a key: both text paths dereference it on the render thread today, so its glyphs are copied instead, on first sight for the string op and at hook 8 for the marker text (section 9).

Wide fog grid. Fogwide already builds its grid on the game thread per LOS change, not per draw. It becomes a second instance of the mailbox (each slot carries its own dimensions, only the write slot grows) rather than a table in the frame packet; its critical section and retire ring go.

7 · the other direction

The renderer asks; the owner of the word writes

The zoom already does this for the camera follow: the render thread raises a request, the game thread consumes it, because the follow slots are pointers the stepper dereferences. The plan makes that the only shape, with two record kinds. The anchor step is a delta, consumed once and accumulated if the game thread is slow, because a latched "the eye should be here" re-applied every draw would pin the camera against the engine's own arrow-key, edge and follow scrolling. The eye hold is a level, the one absolute. Both are applied at the start of the next in-play draw, after the engine's own camera writers for that frame and before the draw reads the eye, so the engine's frame, its fog rebuild and its minimap box all see the commanded eye.

Tooling requests (peek, catalogues, weapon dumps, the GUI snapshot, scenario detection) take the same shape with a small ring: the render thread's file poller posts a request, the observer services it on any frame, in-play or shell, rate-limited, reading per-map memory only on in-play frames. The poller keeps the scenario applier's give-up discipline, a frame budget and a compare-and-swap between "the poller gave up" and "the servicer claimed it", so a stuck game thread costs one clear error instead of a hang or a late answer landing in a reused buffer.

8 · levels

The loader thread, the out-of-game packet, and why the load hole closes

The engine review found what the audit had missed: the level load runs on a loader thread. The game-screen handler creates it at 0x4982CA; its body allocates the particle layers and the projectile array, runs LoadMap, builds the unit array (0x4854A0) and the minimap picture, and as its last act sets bit 1 of main+0x38D75. The game thread meanwhile draws the loading screen, and installs the in-play frame handler only after testing that flag. So "the game thread owns all of main" is false during a load, and true for every in-play draw, which is exactly the set the 0x4969D2 gate selects. The minimap builder's "own thread" is this loader thread.

What the frame packet retires, and what it does not

  • Retired once every render-thread reader of per-frame state is converted: the unit array and pose reads, the fog descriptor read and its guard, the render-thread stores, the deferred FreeObjectState ring (no render-thread code reads an Object3do any more, once the opt-in writeback and render3do paths are converted or deleted).
  • Retired with the GL UI's render half (landing 4c): its engine reads (the viewport, the minimap descriptors and pixels, the view box, the cursor sprite), the loader-thread minimap snapshot, and the font address inside the string op. The GL UI queue itself stays; section 9 says why.
  • Stays until an asset channel lands: the model-template redirects, the teardown wrap, the pass counters and the level generation, because the bake, the bounding boxes and the texture atlas still walk template trees and GAF frames on the render thread, and the terrain atlas reads the tile set. Those are per-level or per-session lifetimes the fence already covers, measured over seven level cycles.
  • The timeout hole (the one-second teardown wait) closes independently by deferring the cascade's remaining frees through the existing ring, the audit's own alternative, in about 150 lines.
  • The optional end state: a level packet (tile set at 1 KB per tile, so 11.8 MB on the biggest stock map; tile map; height bytes; feature defs; type table; minimap picture) keyed on the teardown count and the array pointers, plus assets copied on first sight from a request ring. Then the fence goes entirely and the rule becomes absolute. The migration review rates it the worst risk for its benefit; decide after step 4 with measured numbers.
9 · the GL UI layer

A second transport already runs beside the packet, and it stays one

Since Phase E the engine's UI reaches the screen through GL (GL UI renderer). The first version of this plan carried that in one line, "the GUI op ring stays a ring", and the owner asked whether the line was enough. It was not. The GL UI layer is a second producer and consumer pair with its own control words, four engine reads on the render thread, one publisher on a third thread, and engine code executing on the render thread. None of it breaks the mailbox. All of it has to be scheduled, or the rule in section 10 fails on its first run and the render half is still reading engine memory after landing 5.

How it works today. Observers on every pixel-writing leaf record ops on the game thread. At each flip, at most every 5 ms, the publisher turns them into a batch for a lock-free single-producer, single-consumer queue of 65 536 ops with a 16 MB byte arena (tagpu_gui_int.h): a seed for a surface first seen, a sprite keyed on its GAF frame with the pixels copied on first sight, a copy, a clear, a box of pixels read there and then, and since G17d a string op that carries the string, three colour bytes and the address of the font object. The render thread drains everything queued at every present into retained twins of the engine's surfaces, a UI atlas and a device-resolution sharp layer. The twins are incremental state: every op mutates one, and the sprite identity is what restores UI art under Classic++ and stamps text at the device's resolution. A latest-wins snapshot of the surfaces cannot carry that, so the queue is not a mailbox and does not become one. "Unified" means one rulebook for two shapes: the mailbox for per-frame state, the queue for an op stream, both with an explicit init, the atomic builtins on their indices, one writer per word, and a heartbeat that says what was dropped.

What the plan carried, and what it missed

  • Carried: the queue as one of the seven channels; the packet fields the render half needs (the palette, gamma, GUI colours, the minimap box, the three minimap surfaces, the cursor's geometry and pixels, the true viewport); the render thread's restart across a display-mode switch, for which the GL UI's tagpu_gui_glreset is the existing re-latch point.
  • Missed: the render half still reads engine memory, and no landing converted it. On the render thread tagpu_gui_surf.c reads the true viewport in its layer draw, the minimap descriptors and 13 KB of their pixels per frame, the view box and its colour byte, and the cursor sprite through the graphics globals; its "in a game" gate is the minimap composite pointer being non-null. Rows 2 to 5 of the migration never named the file, so after landing 5 it would still be on the allow-list.
  • Missed: an engine address inside a queue op, dereferenced on the render thread. PK_STRING.frame is the font object captured at the glyph blitter's observer. At drain time, up to the queue's backlog later, twin_string hands it to tagpu_text_glyph, which reads the header, the table and each glyph behind IsBadReadPtr, then calls the engine's blitter with it. The marker text path holds the same kind of pointer from hook 8. "Keys, not pointers" listed the font as a key, and the session-reader class assumed a font lives for the session; no note establishes that.
  • Missed: engine code executes on the render thread, and the rule had no class for it. The blitter is verified pure (gpu-status §2.5: it reads the font and writes our buffer, no globals), and the detour keeps no static state, so the observer chain being re-entered from the render thread is safe. But the address regex flags 0x4CCF60 in tagpu_text.c, and neither "publisher" nor "session reader" describes it.
  • Missed: a publisher on the loader thread. before_minimap (tagpu_gui_leaves.h) runs on the loader thread, measured, and publishes the picture bytes-then-barrier-then-generation: correct on its own, and exactly what "never publish outside the 0x4969D2 gate" forbids. The picture was only in the optional level packet.
  • Missed: two cadences, and the coherence card gave the wrong reason. The GUI batch is published inside the flip, at most every 5 ms, into a queue with a backlog; the packet is published after DrawGameScreen returns, only when the cell is not fresh. The render thread takes one packet at the top of its frame and then drains the queue to empty, so the twin can be ahead of the packet's world. The skew is invisible because nothing in the twin is world-anchored except the engine's minimap box and dots at 1×, not because "the twin is ours". One ordering fact worth having: the GUI publish runs between the observer's before and after, so the commands applied before a draw are what that flip's UI reflects.

What changes

  1. The queue stays, under the same rulebook. Explicit init, the atomic builtins on qHead/qTail and the arena indices, and one writer per control word: the consumer raises reseed and its reason, the producer takes them with an exchange to zero, and the producer's own overflow reasons live in a word of its own. Its stall guard and skip-to-reset are already the "consumer stuck" answer of section 5 for a queue, and they stay.
  2. Font bytes, both text paths. A glyph op on first sight of a (font, code) pair carries the font's three header bytes, the glyph's width and its bit rows, bounded on the game thread where the font is live by the same cell limits the cache applies today; hook 8 copies the marker font's header and its 95 printable glyphs into the packet whenever the pointer or the signature changes. The render thread's glyph cache fills from the arena and the packet, and the blitter is handed a one-glyph font object of ours, so TA's own glyphs are still TA's own blit. No render-thread code dereferences a font, and tagpu_text.c loses its probes.
  3. The render half reads the header and the packet. The true viewport, the minimap box and its colour, the cursor rect and pixels, the three minimap surfaces from their table, the in-game gate from in_game, and the picture from the level's first packet, copied into a consumer-side buffer keyed on the level generation because a later packet replaces the slot and a GL re-init needs it again. The loader-thread observer is deleted.
  4. A third allow-list class, pure engine code. One entry, the blitter, with its disassembly range as the argument (section 10).
  5. The packet echoes the GUI publisher's flip counter. The heartbeat counts the twin-to-packet skew beside the surface-sequence mismatch of section 5, so "invisible" is measured rather than argued.
  6. One landing, 4c, after the fog and before the frees, reviewed high because it changes what crosses between the threads. Its gates are the GL UI's own: the 120-stop strict walk, the sharp minimap A/B, text miss=0.

What this does not change

The twins stay 1:1 with the engine's surfaces, strict keeps meaning what it meant, the census still explains every changed pixel, and the string op still stamps TA's own glyphs. The GL UI's gates remain the oracle for its landing; the packet only changes where its inputs come from.

10 · afterwards

Rules that a build step can check

  1. Every engine address and offset lives in one header, and only publisher files may include it. "Does this file read engine memory" becomes "does it include the header". The draft's grep -l 0x511DE8 would have matched 6 of the 25 files; 19 spell it 0x00511DE8u.
  2. A default-deny allow-list, checked as a prerequisite of the DLL target so make and the CI job both fail on an offender. The check greps every source not on the list for any virtual address (0x0*4xxxxx or 0x0*51xxxx, which also catches the graphics globals, the debris slots in .data and the order descriptors), for IsBadReadPtr, for the header include, and for the ta + 0x conduit through which a "converted" file could still dereference engine memory.
  3. Three classes on the list, each line with its argument: publisher (game thread); session reader (render thread, data that lives for the session and is never rewritten: GAF banks, the cursor table, the shell's palette and gamma; not fonts, whose lifetime no note establishes and whose glyphs are copied instead); and pure engine code (render thread: a function called with our buffers, listed with the disassembly range that shows it reads only its arguments and writes only its destination). The third class has one entry, the glyph blitter 0x4CCF60 to 0x4CD006 in tagpu_text.c, and exists so the rule can name it instead of waving it through as data. The list only shrinks after the first landing; a conversion's diff shows the lines it removed.
  4. Bounds live in the publisher, once. Every value leaving engine memory is checked against the engine's own count before it is copied.
  5. The high review trigger "changes the synchronisation between the threads" becomes "changes the exchange, adds a publisher read, or adds an engine write". A conversion that only moves reads into the publisher and makes a consumer read a struct is medium, provided the primitive carries no engine reads, the producer API lives in a publisher-only header, and the allow-list shrinks in the diff.

The migration review moved the commands up to the second step: the eye is read from the header and written through a command, and zoom-to-cursor couples the two inside one frame, so landing one without the other wobbles on every wheel gesture.

12 · four reviews, and a fifth pass

What the reviews changed

Four independent reviews of the draft, each read-only against the tree and the binary. Their verdicts, and what each forced into this version. A fifth pass on 2026-09-12, prompted by the owner's question about the GL UI layer, is recorded last.

Protocol correctness

Sound, with fixes. The permutation argument holds for every interleaving once it holds initially.
  • The sketch had no init: zeroed statics put both threads on slot 0. Explicit init at DLL attach, slots allocated, head_seq 0 meaning "no packet".
  • The head/tail self-check was blind: both written after the fill. Head before, tail after, compared at frame end against the head latched at acquire.
  • Spell the exchange with the atomic builtin; the mingw InterlockedExchange macro's contract is acquire-only. xchg is implicitly locked, no lock byte; the fork's MemoryBarrier is a locked byte exchange, not mfence.
  • Four orderings, not two; two index bits with the reserved bits asserted; twelve runtime assertions and the heartbeat line. Its strand-never-free growth policy was replaced after the review by reserve-and-commit, which has no old block to strand at all.
  • Three slots without interpolation, four with; the fogwide buffers are the same algorithm made blocking.

Engine feasibility

Buildable, with changes. Verified by disassembly that the flip call sits at 0x46A3DB, returns to 0x46A3E0, and the function returns at 0x46A3FD.
  • The publish point fires per engine draw (330 to 4900 per second), not per presented frame: rate-limit on the cell.
  • One observer on DrawGameScreen, gated on the return address 0x4969D2; not the GUI flip observer (armed only with the GUI layer), not the scenario applier's site (non-chainable), not cnc-ddraw's present (cannot tell a game frame).
  • 0x495A30 is the screenshot function, not a scroll path; its loop draws without flipping.
  • The level load runs on a loader thread; the in-play gate is what closes the load hazard.
  • Feature-grid anchors are per frame, only the height byte is per level; tiles are 1 KB each; the mouse writeback is already a game-thread store; ScrollSpeed is a render-thread store the draft omitted; assets need a third channel or stay behind the fence.

Migration and reviewability

Right end state, wrong order in one place that matters. Stop before the level packet.
  • Commands land with the header, or zoom-to-cursor wobbles for two landings.
  • The build rule lands first as a ratchet, with a real address regex and an allow-list that only shrinks; the draft's grep would have passed the files it exists to catch.
  • Step 3 converts all six unit-array readers or the hazard stays open; the fence cannot shrink until the template walkers are converted.
  • The level packet has the worst risk for its benefit; the audit's own alternative closes the timeout hole in about 150 lines. Tooling stays out of scope.
  • A landing plan with deletes, review level and gates per step, and the twelve places a half-migrated tree could regress silently.

Adversarial

Survives with changes, none to the mailbox itself. Three findings changed the design.
  • Between levels the renderer would draw the dead level over the menus: the teardown post hook publishes in_game = 0.
  • A latched eye command pins the camera against the engine's own scrolling and lags a frame: deltas consumed once, a level for the hold, prediction with cmd_ack_seq.
  • Truncating the units table in slot order drops whole players: size it to the engine's slot count, cull only pieces.
  • Same-tick packets would make the lerp stepped: tick-aware give-back. The producer stamps the tick start with the performance counter, never GetTickCount.
  • The render thread is joined, never killed; SEH is not a guard; TA is not classic lockstep; the memory headroom is real and the draft's level sizes were 2 to 4× low.

The GL UI layer

Carried in one line, and the line was not enough: a second transport with its own reads, a third-thread publisher and engine code on the render thread. None of it breaks the mailbox; all of it is now scheduled (section 9).
  • The op queue stays a queue: the twins are retained state and sprite identity is what restores art and stamps text. Two shapes, one rulebook.
  • The render half reads engine memory in four places and no landing converted it: landing 4c.
  • The string op carries a font address the render thread dereferences and then hands to the engine's blitter: glyph bits on first sight, both text paths, and a third allow-list class for the blitter.
  • The minimap picture is published from the loader thread, the one publisher the in-play gate forbids: the level's first packet carries it.
  • The twin travels on the other channel; the coherence card gives the right reason now, and the packet echoes the GUI publisher's flip counter so the skew is counted.

Still to verify before the first landing

  • Whether bits 0 and 1 of main+0x38D75 are reset between two games in one process. Settled by landing 1's log (2026-09-12): no instruction clears them, and the packet's per-frame copy of the word reads 0x0003 at a level's first in-play draw and 0x0000 a few seconds later, so a bulk store zeroes it after the load; the level-cycle run then read 0x0000 at the level end and 0x0001 at the next loader's entry, so a second game starts from zero and bit 1 is a fresh fact for every level.
  • The loader thread's identity as a direct measurement. Measured by landing 1: an observer on the thread's entry 0x497C70 logs its id (756 against the game thread's 736 on the first run) and, at its return, that the level's first in-play packet had not yet been published — the order the gate rests on, in the log.
  • Real particle counts over a 200v200 run, to size the sub-particle arena.
  • Whether the engine's cursor worker thread is live in the fork's windowed configuration; it touches the graphics globals the cursor read copies, and the exposure is one wrong cursor rect.
  • Whether the tick of the packet in the cell can be carried in the cell word's spare bits, or the consumer takes first and chooses what to hand back at the next acquire.
  • The lifetime of a UI font object: where the engine loads and frees the font set behind [0x51FBA4]+0x14. Until that is read out of the binary, the glyph copy is the argument and no lifetime is claimed.
  • The twin-to-packet skew, measured: the GUI publisher's flip counter echoed in the packet and counted on the heartbeat over a scrolling 200v200 minute, before deciding whether the minimap box needs pairing at all.
