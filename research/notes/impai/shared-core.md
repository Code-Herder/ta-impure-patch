# Layers and modules

One copy of the simulation and of the player-facing rules, shared by the in-game wiki, tasim, ImpAI and the game. The simulation is written once, in the shared core `tasim_*.c` (S1 carved it out of `tagpu_wikisim.c`, which keeps the wiki's front end); the wiki's mockup plays the same C through a host process ([sim.js retired](sim-js.html)), so it carries no copy of its own. The player-facing rules -- Quick Build and the snap, the placement gesture, the reclaim sweep -- are written once too, in `tasim_snap.c`, `tasim_place.c` and `tasim_sweep.c`, which the game's `tagpu_resource.c`, `tagpu_place.c` and `tagpu_sweep.c` and the wiki's front end call through `WORLDQ`.

## The layers

| Layer | What | Used by |
|---|---|---|
| **Consumers** | the wiki front end; the tasim harness; the ImpAI brain; the game's features (Quick Build, placement, the reclaim sweep) | — |
| **Shared rules** | placement, snapping and sweep rules, engine-free | every consumer, through `WORLDQ` |
| **`WORLDQ`** | one read-and-order interface (`worldq.h`), with two implementations: the core's (`tasim_worldq.c`), and the engine's in `ddraw.dll` (`tagpu_worldq.c`) | the rules, ImpAI, the game's features |
| **The core** | the simulation, `tasim_*` | the wiki and tasim, which own a world |

The wiki and the tasim harness own a world and call the core directly. ImpAI and the game's features see the world only through `WORLDQ`, so the same rule code runs in the game, in a wiki demo and in a headless game.

The core keeps `tagpu_wikisim.c`'s discipline: no globals, all state in a struct its caller owns (`TASIM`, beside the definitions it plays, `TASIM_DEFS`), doubles with each operation rounded once (SSE2 in the DLL), no clock, a state hash and a fork. It is built three ways from one source: i686 in `ddraw.dll`, native x86-64 for tasim and tests, and the mockup's host ([sim.js retired](sim-js.html)). `tasim_combat` is not built yet: its standalone pieces are (`tasim_proj`, `tasim_ballistic`, `tasim_dmg`, `tasim_fxgate` in the table below), and the combat tick that calls them is not.

### The core as built

The files are `tagpu/ddraw/src/tasim_*.c` over one internal header, `tasim.h` (the shared vocabulary -- `CELL`, `XZ`, `BOX`, `TARGET` -- the small helpers every module reads, `static inline`, and each module's functions), with `tasim_state.h` for the state and `tasim_defs.h` for the definitions. The public API of the wiki is still `tagpu_wikisim_*`. Every function moved whole: its body is the one it had in `tagpu_wikisim.c`, with a shared function's name prefixed `tasim_`, reading the `TASIM` and the `TASIM_DEFS` where it read the `WIKISIM`, as `simparity.mjs` proved against `sim.js` natively and under Wine before S2 retired it. Today `simparity.mjs` holds the core's three builds -- native, under AddressSanitizer, and i686 under Wine -- to one another play for play, through the wiki's simulation host (`tagpu/ddraw/tests/wikihost.c`).

### The state

**`TASIM` is the core's state and `TASIM_DEFS` the definitions it plays** (`tasim_state.h`). `TASIM` holds what a simulation of the core is, in the representations the wiki's simulation has always had: the map (`W`, `H`, SurfaceMetal, the pace, each cell's metal and fog, the summed metal `rich`, the vents), the units on the heap in creation order with string ids, double positions and each one's order list (`unit`, `nunit`, `cunit`, `next_id`, `next_serial`), the features standing and the cells of those gone, a game's seats' economies, kills and deaths, the viewed seat, the COB host and its facts, the nano spray, the sound with its quiet flag and the scene's last serial, the movement's scratch, the tick and `oom`. `TASIM_DEFS` holds the entry the sim plays (with a casting, the bound entry): its unit types and its features table; the core reads it and never writes it. The record types the core is made of (`WIKIUNIT`, `WIKIORDER`, `WIKIFEAT`, `WIKILEDGER`, `WIKIECON`, `WIKIDEATH`, `WIKIRECT`, the spray's and the sound's) live in `tasim_state.h` too, with their engine comments. A core function takes the `TASIM` when it reads or writes the state and the `TASIM_DEFS` when it reads a definition.

The wiki's `WIKISIM` embeds both, as `sim` and `defs`, and keeps beside them only what is the front end's: the input seats, the script and the demo's clock, the sidebar, the casting's binding, the view and its arrays, the clicks. `tasim_map_alloc` makes the map's arrays and the movement's scratch for a map's size, and `tasim_free` frees everything a `TASIM` holds.

**The boundary.** No core file includes `tagpu_wikisim.h`: the core reads its `TASIM`, its `TASIM_DEFS`, the entry's rows (`tagpu_wikidata.h`) and the COB host (`tagpu_wikicob.h`). `tests/tasim_link_test.py` links every `tasim_*.c` and what the core calls, without `tagpu_wikisim.c`, plays one builder through a walk, a build and a kill for 300 ticks on a `TASIM` made by hand, and holds the native, sanitized and i686 builds to one output.

**The unit hook** is the core's one call into its owner, `TASIM.hook` with `hook_ctx`, at three points of a unit's life: ENTER once the unit is in the list and before its script spawns, LEAVE before it is freed, BUILT when a structure's build reaches 1. The wiki's hook sets a unit's page state from its sidebar's layout, forgets the sidebar's shown unit, and counts the player's finished buildings for the demo's waits. It runs synchronously, at the instant and on the thread of the core's call, so its writes keep their place among the core's; its contract (`tasim_state.h`) is to write its owner's state and the unit's `bp` and `page` only, read nothing of the core but the unit, and never call back into the core. The hook's context is the `WIKISIM`'s own address, so a `WIKISIM` stays where `tagpu_wikisim_init` made it. A headless `TASIM` has no hook.

What the core used to read of the front end is now state or an argument: the viewed seat is `TASIM.viewed`, which the front end sets through `tasim_set_viewed`; the sound's quiet flag and the scene's last serial are `TASIM`'s; the tick a kill is fed on is `tasim_kill`'s `feeding`.

**The state hash** is one FNV-1a stream (`tasim_hash.h`: the helpers `fnv_bytes`, `fnv_int`, `fnv_double`, `fnv_str`). `tagpu_wikisim_hash` feeds the core's items through the core's feeders -- `tasim_hash_map` (item 2), `tasim_hash_units` (3), `tasim_hash_cob` (8's host), `tasim_hash_fx` (9 and 10), `tasim_hash_feats` (11's features), `tasim_hash_econ` (12) and `tasim_hash_deaths` (14) -- in their place among its own items, on its one running state, so every value is the one the wiki's hash has always had. `tasim_hash` is the core's own: the tick and the feeders in the same order, from the offset basis.

**The combat pieces** are functions of their arguments alone: none holds a stream, a clock or a pool of its own, so the combat tick (T2a and on) owns the projectile array, the draws and the effect pools' calendars, and calls them. `tests/tasim_combat_test.py` holds them in the three builds to their hand-checked cases from the disassembly, to literal ports of the engine's compaction and burst over random pools, to brute-forced shatter flights over random terrain, and to one digest; in the i686 build it runs the engine's own x87 sequences for the pitch solver, the cruise distance, the damage factor, the box distance and the falloff, and finds 2 000 000 of 2 000 000 random inputs equal in each, none of the solver's differing by R4.

**The engine's numbers.** The core computes as the engine does, not as libm does: `tasim_fixed.c` carries its own atan2, sin and cos, so the three builds agree bit for bit (`tests/tasim_fixed_test.py` holds them to one digest), and it emulates the engine's `_hypot` rather than calling a hypot, because the engine's is not correctly rounded and lands one below an integer distance in about one integer-distance pair in ten ([cob](../engine/cob.html), `0x4FB440`). The test also runs the engine's own x87 sequences for `_hypot`, the angle `0x4B715A` and the rotator `0x4B7173` in the i686 build and requires the core's answers equal; the angle and the rotator are the residuals R1 and R2 of the T1 plan, a rounding tie the fdlibm routines could break otherwise than `fpatan` and `fsincos`, and none showed in 10⁶ calls of each.

Where the core as built differs from the table above:

- **Two definition tables until the wiki's old rules retire.** `tasim_defs.h` is the wiki's accessors over `WIKIDEF`, whose doubles are the inputs of the wiki's own rules; its loader is still `tagpu_wikidata.c`'s, and the casting's binder (`bind`) is still the front end's. The engine's definitions are `tasim_keys.c`'s, read from an install by the harness's install loader (`tools/tasim/tasim_load.c`) and compared with a running game's tables by `tools/tasim/defcheck.py`. The loader is the harness's, not the core's, because the wiki's host build links every `tasim_*.c` without the file modules `tagpu_vfs` and `tagpu_tdf`. No key is converted twice: the wiki's castings move onto `tasim_def_key` as each rule reading a `WIKIDEF` field retires, the movement fields when the wiki plays the engine's movement and the build and economy fields with the engine's economy (the T1 plan's b5, c3 and c6).
- **Two grids until the arena (b1).** The wiki's simulation plays on `TASIM`'s grid; the engine's -- `tasim_map.c`'s cells, `tasim_class.c`'s maps and `tasim_path.c`'s pathfinder -- are standalone structures in memory their caller gives (`ts_map_bytes`, `ts_class_bytes` and `ts_pf_bytes` size it; the pathfinder's pool is sized to one node per cell, the bound a search cannot exceed, where the engine grows it). `tools/tasim/classmap.c` fills the grid and the maps today -- the install loader's interface below is what b1 wires into `tasim_load.c` -- and `tests/tasim_pf_test.c` alone runs the pathfinder; nothing in the wiki reads any of them. b1 moves them into the arena. The core holds 0 where the engine leaves its allocator's bytes: the back-reference of a cell never spawned on, flags bits 2 and 7, and the 2x2 extremes of the last column and row, which LoadMap never computes. The class rule `0x47DE60` reads the last row's, and the last column's under a non-blocking feature anchored there, which the border mask leaves in place ([map](../engine/map.html), *The cell*); `classcheck.py` reports the engine's values in both.
- **`tasim_cob` is the binding, not the host.** The host stays `tagpu_wikicob.c` under its own name, which the wiki's simulation host (`wikitest serve`) and `serve.py`'s `POST /cob` build with it.
- **The fork stays in the front end,** with the view and the other entry points: it rewrites the script, the front end's. The state hash is the front end's too, over the core's feeders ([the state](#the-state)).
- **The spray and the sound are in the state hash** (`tagpu_wikisim.h`, items 9 and 10), as before the carve; taking them out is a change of behaviour, not S1's.
- **The front end keeps no copy of the rules.** It builds each rule's input -- the acting seat's selected units in slot order, the cursor, Shift, the armed type -- opens the core's `WORLDQ` on the acting seat and calls `tasim_snap`, `tasim_place` and `tasim_sweep`, so a demo plays the game's rule. It keeps the selection helpers (`is_builder`, `is_reclaimer`), `unit_at` and the grid's fog reads (`seen`, `flat`) for its own stock-click paths and the view.
- **The core reads nothing of the front end's.** The sidebar's page state of a unit and its shown unit are the front end's, kept through the unit hook ([the state](#the-state)); the acting seat's input state (`ST`) and arming a building (`arm`, `disarm`) are the front end's alone, and the core's `WORLDQ` opens on the seat its caller names.

### The install loader's interface

The loader makes a map in four calls, all of them `tasim_map.h`'s and `tasim_class.h`'s, and holds the memory:

1. `ts_map_bytes(W, H, pool)` and `ts_map_init(&map, mem, bytes, W, H, sea, pool, fd, nfd)`: W and H the TNT header's +4 and +8 (16-px cells), the sea level its +0x24's low byte, `pool` the wreck pool's records (`TAGPU_LIM_WRECKS`, the raised build's 8192), `fd` the FeatureDefs in the engine's order -- each name of the TNT's table in turn, one `tasim_featuredef_read` of the first `features/**.tdf` section of that name, then each schema feature's name that no def has yet without case, appended the same way.
2. `ts_map_load(&map, &in)` with a `TS_MAPLOAD`: the TNT's version and attribute records, the schema's `SurfaceMetal` and GlobalHeader's `lavaworld` (each the engine's `atol`, default 0), and the schema's `[features]` as `TS_MAPFEAT`s in file order, each name resolved to its def index, `XPos` and `ZPos` its position in cells (default -1), and a record with either negative passed with def -1.
3. `ts_class_bytes(cls, W, H)` and `ts_class_init(&cm, mem, bytes, cls, &map, units, &bad)`: `cls` moveinfo.tdf's 32 classes read by `tasim_moveclass_read` (an absent `[CLASS<i>]` not present), `units` the units' view, NULL while there are none.
4. `ts_class_fill_all(&cm)`, as `0x440940` runs it after LoadMap.

`tools/tasim/classmap.c` is the four calls on values a caller pipes in: `classcheck.py` feeds it the files its readers read.

The build lists take the core by its name: the Makefile compiles every `src/tasim_*.c` on SSE2 with `tagpu_wikisim.c`, `tools/wiki/tasimsrcs.mjs` lists them for `wikibuild.mjs` (the simulation host's three builds), `framecheck`, `scenecheck`, `stagecheck` and `sidecheck`, and `wikilaycheck.py` and `tests/tasim_link_test.py` glob the same files.

## The shared rules

| Module | Holds | Comes from | Wiki | tasim | ImpAI | Game |
|---|---|---|---|---|---|---|
| `tagpu_placegeo` | the shapes and the take-off arithmetic, integers only | shared | ● | ● | ● | ● |
| `tagpu_sweepgeo` | the ring's test and the split, SSE2 | shared | ● | | | ● |
| `tasim_snap` | the extractor and vent snap, the patch scan, the queued-plan rules, Quick Build's choice and commit | `tagpu_resource.c` | ● | ● | ● | ● |
| `tasim_place` | the gesture's builders, each site judged by the view's site test, the take-offs, the commit's removals and appends | `tagpu_place.c` | ● | | ● | ● |
| `tasim_sweep` | which features a ring takes, the reclaimers' split inputs, the commit's removals and appends | `tagpu_sweep.c` | ● | | | ● |

Each rule is engine-free and reads a world only through the `WORLDQ` it is given: a const ops table and an instance opened for one call on one seat, copying lists into the caller's scratch. The engine's view (`tagpu_worldq.c`) bounds every read as the game's modules did, enters the order roots `0x43ADC0`, `0x43AFC0` and `0x439F80` only after re-deriving the unit from its slot, and removes a node only while its place still holds the action, position and flags the copy had; the core's (`tasim_worldq.c`) numbers units and types as the engine does (slot = index + 1, type = entry type + 1, 16.16 positions). `WQ_MAP.list_cap` is the world's own bound on a list: 0 in the engine, `PLACE_LIST_CAP` in the core. Two answers differ between the views by construction: the engine's mapped test answers by the viewed player's bit (`0x408090` tests `1 << main+0x2A43`, [map](../engine/map.html)), so its view asks it only for the viewed seat and the controlled one (`main+0x2A42`, whose reclaim the resolver's mode 12 judges by that same bit) and refuses a mapped query for any other seat, while the engine's site test and its resolver's reclaim read that bit whatever seat asks, so for another seat they answer by the viewer's map (`worldq.h`, beside `site_ok` and `can`); and the core's mapped test is the 16-px explored cell, not the engine's sheared 32-px block. The engine's build options are each seat's own: `WqMenuFn` takes the seat, and the menu is read from that seat's side's pages.

## What stays outside

- **The wiki front end:** the UI emulation (the cursor, the sidebar's gadgets, the page router, what a press lands on, the click window, the acting seat's input state and arming a building); scripted input (the build and pick trips, the glide, the input timeline); selection and casting. Drawing is already in separate files.
- **The tasim harness:** a C driver, `tasim_run` (load, seat the brains, run, print JSON), built for i686 too so whole games get the Wine parity check; the install loader `tools/tasim/tasim_load.c`, which every harness command that needs an install's definitions reads it through; and Python in `tools/tasim/` for tournaments, Elo, sweeps and calibration. Nothing goes into the harness that the wiki or ImpAI could need; that goes into the core.
- **The install loader** reads an install as the engine finds its files (`tagpu_vfs` over a mount list, `tagpu_tdf`), with the folders and the first mount pattern a mod's loader renames in memory given to it, and fills the core's definitions through the key table: the move classes, the units the menu-time pre-scan keeps (its `Version`, `Copyright` and archive tests, [tasim](tasim.html)) in the def array's `_stricmp` order (a type is its row + 1, type 0 being the engine's `None`), each unit's class record winning over its own keys, the weapons in the slots their IDs name, each weapon's `[DAMAGE]` rows, the features, each builder's build options by the sidebar's page rule, and the named-not-modelled report with the engine behaviours of `tools/tasim/engine-features.tsv`. `tasim_run`'s `defs`, `roles` and `values` read through it, and so through them do `defcheck.py`, `duelgen.py`, `roles_check.py` and the key table's test.
- **No C++.** The core, the rules and the brain are C.

## The order

S1 carved the core with no change in behaviour while `sim.js` still existed, so that `simparity.mjs` proved it. S2 retired `sim.js`: the mockup and the node checks play the core through the host, and `simparity.mjs` holds the host, the sanitized build and the i686 build under Wine to one another. S3 moved the game's rules above `WORLDQ` ([landings](landings.html)).
